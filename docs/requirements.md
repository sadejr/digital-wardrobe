# Requirements – Digital Wardrobe (first version)

This document defines the requirements, the data model and the scope of the first version of the Digital Wardrobe application. Each requirement has an ID so that it can be referred to from tests, commits, pull requests and the README.

## 1. Functional requirements

### 1.1 User accounts

- **FR-1** A visitor can register an account with an email address and a password.
- **FR-2** A registered user can log in and log out.
- **FR-3** All wardrobe pages require login, and a visitor who is not logged in is redirected to the login page.

### 1.2 Clothing items

- **FR-4** A user can create a clothing item with a required name and the optional fields brand, category, colours, seasons and one photo.
- **FR-5** Category is a single value chosen from a fixed list: tops, trousers, outerwear, shoes and accessories.
- **FR-6** Colours are free text, an item can have several colours, and colour values are trimmed and stored in lowercase.
- **FR-7** Seasons are chosen from a fixed list of four values (spring, summer, autumn, winter), and an item can have several seasons.
- **FR-8** A user can add a photo by uploading a file or by taking a picture with the camera of a mobile device.
- **FR-9** A user can view the details of a single item.
- **FR-10** A user can edit an item, including replacing or removing its photo, and a replaced or removed photo is deleted from storage.
- **FR-11** A user can delete an item, which also deletes its photo and its tag assignments but not the tags themselves.

### 1.3 Wardrobe views

- **FR-12** A user can switch between two views of their items: a compact view showing a small photo and the item name for each item, and a large view showing fewer items with bigger photos.
- **FR-13** Items without a photo show a placeholder image in both views.
- **FR-14** Items are shown in pages of 24 items, and photos are loaded only when they come into view (lazy loading).
- **FR-15** The selected view, filters, search terms, sorting and page number are kept in the page URL, so that a filtered result can be refreshed or bookmarked.

### 1.4 Tags

- **FR-16** A user can create, rename and delete their own tags, and tag names are unique per user.
- **FR-17** On the item form, a user can open a tag window where they can select existing tags or create a new tag, and an item can have several tags.
- **FR-18** A user can remove a tag from an item.
- **FR-19** Deleting a tag removes it from all items that use it, without deleting the items.

### 1.5 Filtering, search and sorting

- **FR-20** A user can filter their items by category, colour, season and tag.
- **FR-21** When several filter types are used together, an item is shown only if it matches all of the selected filter types.
- **FR-22** When several values of the same filter type are selected for tags, colours or seasons, the user chooses whether an item must match all selected values (AND) or at least one of them (OR).
- **FR-23** When several categories are selected, an item is shown if it matches any of them, since each item has only one category.
- **FR-24** A user can search by item name using a separate name search field.
- **FR-25** A user can search by brand, colour and tag name using a second search field.
- **FR-26** Both searches are case-insensitive and match part of a word.
- **FR-27** A user can sort their items by name and by date added.

## 2. Non-functional requirements

### 2.1 Security and data isolation

- **NFR-1** Every database query for items, tags and photos is limited to the data of the current user.
- **NFR-2** Every ID received from the client, including tag IDs submitted with an item form, is checked for ownership before it is used.
- **NFR-3** A request for data that does not exist and a request for data owned by another user return the same "not found" response.
- **NFR-4** Photos are not stored in a public folder and are returned only through a controller action that checks ownership.
- **NFR-5** Passwords are hashed and managed by ASP.NET Core Identity, and accounts are temporarily locked after repeated failed login attempts.
- **NFR-6** All requests that change data, including requests sent from JavaScript in the tag window, are protected with anti-forgery tokens, and the deployed application uses HTTPS only.

### 2.2 File uploads and storage

- **NFR-7** Only JPEG, PNG and WebP images are accepted, and the file type is checked from the file content and not only from the file extension.
- **NFR-8** The maximum size of one photo is 10 MB.
- **NFR-9** The file name in storage is generated by the server and is not based on the name of the uploaded file.
- **NFR-10** File storage is accessed through an interface, and the first version stores files on disk in a Docker volume.

### 2.3 Usage limits

- **NFR-11** A user can have at most 100 clothing items, which also limits each user to 100 photos.
- **NFR-12** A user can have at most 100 tags.
- **NFR-13** All limits are checked on the server and not only in the user interface.
- **NFR-14** All limits are stored in the application configuration, so that they can be changed without changes to the code.

### 2.4 Usability and error handling

- **NFR-15** All pages are usable on mobile screens as well as on desktop.
- **NFR-16** Validation errors, including errors caused by reaching a limit, are shown next to the related form fields with a clear message.
- **NFR-17** Unexpected errors show a general error page without technical details, and the error is logged on the server.

### 2.5 Development and deployment

- **NFR-18** The application and PostgreSQL can be started locally with one Docker Compose command.
- **NFR-19** The database schema is managed with Entity Framework Core migrations.
- **NFR-20** Automated tests run in GitHub Actions on every push and pull request, and the tests include checks that one user cannot read, change or delete another user's items, tags or photos.
- **NFR-21** The first version is deployed and publicly accessible, and the repository contains an open-source licence and a README describing the architecture, the main technical decisions and the setup and deployment steps.

## 3. Data model

The user table is created and managed by ASP.NET Core Identity. The application adds the following tables.

```
ClothingItem
Id            int          primary key
UserId        string       owner, foreign key to the Identity user, required
Name          string       required
Brand         string       optional
Category      enum         optional, single value
Colours       text[]       optional, multiple values, stored in lowercase
Seasons       enum[]       optional, multiple values
ImageKey      string       optional, file name generated by the server
CreatedAt     timestamp
UpdatedAt     timestamp

Tag
Id            int          primary key
UserId        string       owner, required
Name          string       required, unique together with UserId

ClothingItemTag
ClothingItemId  int        foreign key to ClothingItem
TagId           int        foreign key to Tag
                           primary key on (ClothingItemId, TagId)
```

Tags use a join table because they are created by users, can be renamed and are shared between many items. Seasons use an array because they are a fixed list defined in the code. Colours use a text array because they are free text with several values per item but do not need to be renamed across items.

## 4. Out of scope for the first version

The following are not part of the first version: email confirmation and password reset, outfits, outfit collections and outfit planning, wardrobe statistics and usage tracking, AI features, wardrobe sharing, the occasion field, more than one photo per item, background image processing and thumbnails, caching, rate limiting, offline support, translations and paid user plans.

## 5. Known limitations of the first version

- A user who forgets their password cannot recover their account, because password reset is not included.
- Photos are stored and shown in their original size until thumbnail generation is added in phase 2, so pages with many large photos load more data than necessary.
- Free-text colours cannot be renamed across all items at once, and different spellings of the same colour are treated as different values.
